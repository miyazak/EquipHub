# テスト観点の作成

Issue の受け入れ条件を、確認できるテスト観点に分解する。作成したテスト観点は Issue にコメントとして記録し、実装・レビュー・動作確認で使う。

## 前提

- `gh` CLI がインストール済みで、`gh auth status` が成功すること
- 自動テスト（`npm test`、`test/` 配下）がある。テスト観点は、自動テストの追加・修正と、自動テストでは確認できない画面などの手動確認に使う

## 手順

1. 対象 Issue を読む: `gh issue view <番号> --json title,body,labels,comments`
   - 受け入れ条件がない、または検証できない書き方の場合は、テスト観点を作る前にユーザーに受け入れ条件の追記を提案する
   - 既にテスト観点のコメントがある場合は、更新か新規作成かをユーザーに確認する
2. 関連するコードを読む（API は `src/server.js`、画面は `public/index.html` と `public/app.js`）
   - 入力値のチェック、エラー時のステータスコード、状態（`available` / `borrowed`）による分岐を確認する
3. 受け入れ条件ごとに、下の観点でテスト観点を洗い出す
4. **Issue に記録する前に、テスト観点をユーザーに確認してもらう**
5. Issue にコメントとして記録する。本文は一時ファイルに書いて `--body-file` で渡す

   ```bash
   gh issue comment <番号> --body-file <コメントファイル>
   ```

6. コメントの URL と、観点の件数（受け入れ条件ごと）を報告する

## 観点

| 観点 | 例 |
|---|---|
| 正常系 | 必須項目をすべて正しく入力すると貸出できる |
| 異常系 | 必須項目がない、存在しない備品 ID を指定する |
| 境界値 | 返却期限が今日 / 昨日 / 明日、空文字・空白のみの入力 |
| 状態の組み合わせ | 貸出可の備品を返却する、貸出中の備品を貸し出す |
| 画面 | 操作後に一覧とサマリーの件数が更新される、エラーメッセージが表示される |
| 既存機能への影響 | 変更していない API や画面が従来どおり動く |

該当しない観点は省略してよい。

## コメントのテンプレート

```markdown
### テスト観点

対象: #<番号> <タイトル>

| No | 受け入れ条件 | 観点 | 前提 | 操作 | 期待結果 |
|---|---|---|---|---|---|
| 1 | <受け入れ条件の要約> | 正常系 | <データの状態> | <API 呼び出しや画面操作> | <ステータスコード・画面の表示> |
| 2 | <受け入れ条件の要約> | 異常系 | | | |

### 確認方法

- API: `test/` に自動テストを追加し、`npm test` で確認する（自動テストにしない観点は、`npm start` で起動したアプリに `curl` などでリクエストを送って確認する）
- 画面: http://localhost:3000 で操作する
- 確認で `data/db.json` が書き換わるため、確認後は元のデモデータに戻す

### 補足

- <受け入れ条件から読み取れなかった仕様や、判断が必要な点>
```

## 書き方のルール

- 期待結果は、ステータスコードや画面の表示など、第三者が判定できる形で書く
- 受け入れ条件に書かれていない仕様（例: 空白のみの借用者名を許すか）は、勝手に決めずに「補足」に挙げる
- 現在の実装と受け入れ条件が食い違う場合（例: 過去日を拒否していない）は、その観点が現状では失敗することを「補足」に書く
