# PR 作成

現在の変更から、Issue に紐づいた Pull Request を作成する。

## 前提

- `gh` CLI がインストール済みで、`gh auth status` が成功すること
- `gh` が使えない場合は、ブランチの push までを行い、PR のタイトルと本文を Markdown で出力し、ユーザーに手動での作成を依頼する

## 手順

1. 状況を確認する: `git status`, `git diff`, `git log --oneline main..HEAD`
2. 対応する Issue 番号を確認する。ブランチ名・会話から分からない場合はユーザーに聞く。Issue がない場合は先に `create-issue` スキルでの起票を提案する
3. `main` にいる場合は、ブランチを作成する: `<type>/<issue番号>-<短い英語の説明>`。作成したら、Project 上の Issue の Status を `In progress` に変更する（手順は AGENTS.md の「Status の変更」）。既に `In progress` 以降の Status であれば変更しない
4. README の更新要否を確認する。機能を追加・変更・削除した場合は、README.md の「現在できること」「API」、主な制約が実装と一致するよう同じ PR で更新する（AGENTS.md の開発フロー 5）。更新が必要なのに含まれていなければ、コミット前に更新する
5. 無関係なファイル（例: `terminal-check.txt`、`data/db.json` の動作確認による書き換え）を含めていないか確認する。`git add -A` は使わず、ファイルを指定して add する
6. コミットする。メッセージは `#<issue番号> <type>: <要約>`（AGENTS.md の規約に従い、1 行目の先頭に必ず Issue 番号を付ける）。エディタを開かず `git commit -F <ファイル>` で渡す（`#` で始まる行がコメントとして消えるのを防ぐ）
7. 動作確認する。`npm test` を実行してすべて成功することを確認する。画面を変更した場合は `npm start` で起動して確認する。確認で `data/db.json` が書き換わった場合は元に戻す
8. push する: `git push -u origin <ブランチ名>`
9. 下のテンプレートで本文を作り、**作成前にユーザーにタイトルと本文を確認してもらう**
10. 作成する。本文は一時ファイルに書いて `--body-file` で渡す

   ```bash
   gh pr create --base main --title "<タイトル>" --body-file <本文ファイル>
   ```

11. 作成された PR の URL を報告する。あわせて、マージ後に Issue のクローズと Status の `Done` への遷移を確認する必要があることを伝える（自動で反映されなかった場合の対応は AGENTS.md の開発フロー 7）

## タイトル

`#<issue番号> <type>: <要約>`（コミットメッセージの 1 行目と同じ形式）

例: `#12 fix: 過去日の返却期限を拒否する`

## 本文テンプレート

`.github/pull_request_template.md` と同じ構成にする（変更する場合は両方をそろえる）。

```markdown
Closes #<issue番号>

## 変更内容
- <何をどう変えたか>

## 動作確認
- [x] <実際に行った確認と結果>

## README の更新
- [x] <更新した（更新した箇所） / 不要（理由）>

## AI 生成部分
- <AI が生成・修正した箇所（ファイル名と内容）>

## 人間レビュー観点
- <レビュアーに特に見てほしい点（仕様判断、エッジケース、影響範囲など）>

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

## 書き方のルール

- `Closes #<番号>` は必ず本文の先頭に置く（マージ時に Issue がクローズされ、Project 上で Done に遷移する）
- 「動作確認」には、実際に行った確認だけを書く。未確認の項目はチェックを付けずに「未確認」と明記する
- 「README の更新」は、更新した場合はその箇所を、不要な場合はその理由を書く
- 「AI 生成部分」は具体的に書く。人が手直しした箇所があれば区別する
- 「人間レビュー観点」は、仕様上の判断を伴った箇所や、確認しきれていない点を優先して挙げる
